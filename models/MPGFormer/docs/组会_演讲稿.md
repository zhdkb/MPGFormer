# MPG-Former 组会汇报演讲稿

> 对应 PPT：`models/MPGFormer/docs/组会.pptx`  
> 建议汇报时长：10-15 分钟  
> 汇报主线：先说明云工作负载预测的现实需求，再引出“预测证据随窗口状态变化”的研究动机，最后按照 MPG-Former 的数据流解释 Target RevIN、时间证据分支、多尺度原型分支、动态图分支和漂移感知融合。

## 第 1 页：标题页

各位老师、同学好，我今天汇报的题目是 **MPG-Former: Drift-Aware Multi-scale Prototype-Graph Transformer for Cloud Workload Forecasting**，中文可以理解为“用于云工作负载预测的漂移感知多尺度原型图 Transformer”。

这项工作的核心问题是云平台中的 workload forecasting，也就是根据过去一段时间的工作负载变化，预测未来一段时间的负载水平。这里的 workload 可以是 CPU 使用率、QPS、内存占用，或者其他云服务运行状态指标。

我这次汇报主要围绕三个问题展开：第一，为什么云工作负载预测值得单独研究；第二，真实云负载预测的核心难点是什么；第三，MPG-Former 如何通过多种证据建模和漂移感知融合来完成预测。

## 第 2 页：研究动机——云平台中的工作负载预测

首先来看研究背景。

云平台为什么需要做工作负载预测？主要有三个直接应用场景。

第一是自动扩缩容。云服务的负载通常会随时间变化，如果模型能够提前预测负载即将升高，系统就可以在高峰真正到来之前提前扩容，避免响应延迟和服务拥塞。反过来，如果预测到负载将要下降，平台也可以及时释放资源，降低资源浪费。

第二是资源预留和容量规划。云平台上同时存在在线服务、批处理任务、微服务调用链和后台维护任务。如果没有对未来负载的判断，这些任务可能会互相挤占资源。准确预测可以帮助调度器提前规划容量，减少任务排队和资源争抢。

第三是 SLA 与成本之间的平衡。资源分配太少，会影响服务质量；资源分配太多，又会造成成本和能耗浪费。因此，预测的目标不是简单地追求数值拟合，而是支撑实际云平台中的资源管理决策。

但是，真实 workload 的变化来源非常复杂。一方面，它受到用户行为影响，比如日周期、活动流量、区域差异；另一方面，它也受到系统行为影响，比如调度、迁移、维护、限流和批量任务启动。此外，云平台内部还存在共享上游流量、资源竞争和同类实例协同波动等耦合现象。

所以这里有一个关键观察：即使服务、机器和应用都不是新的，同一个 workload 在正常运行中也会经历稳定周期、突发、协同波动和漂移等不同状态。不同状态下，模型最应该相信的预测证据并不相同。

## 第 3 页：研究动机——预测证据会随窗口状态变化

这一页进一步说明刚才的核心观察。

我们可以把同一条 workload 序列切成很多时间窗口。虽然这些窗口来自同一个服务或者同一个实例，但它们的运行状态可能完全不同。

第一类是稳定周期窗口。这类窗口中，曲线具有比较清晰的周期性和节律性，比如每天固定时段流量升高，夜间流量下降。在这种情况下，历史节律和多尺度周期模式对预测未来很有帮助，模型应该更多依赖时间记忆和典型周期形态。

第二类是突发高负载窗口。这类窗口中，最近几个时间点可能突然出现尖峰。此时，长期平均趋势不一定可靠，因为尖峰可能只由很短时间内的局部变化触发。因此，模型更应该关注短期局部变化，比如最近几个点的快速升高。

第三类是协同波动窗口。云平台中多个实例可能同时受到同一个上游流量、同一批调度任务或共享资源竞争的影响，从而出现同步上升或同步下降。此时，仅仅看当前实例自身历史是不够的，其他近期行为相似的 workload 也可以提供外部证据。

第四类是漂移或非典型窗口。这里不是简单的尖峰，而是当前窗口整体的均值、方差或形态已经偏离过去的典型模式。如果模型仍然按照旧周期或旧原型直接外推，就容易把新的状态误认为历史噪声，从而产生系统性误差。

因此，我把这个问题总结为：云工作负载预测不仅是时间建模问题，也是证据选择问题。模型需要判断当前窗口到底应该相信时间历史、典型原型，还是跨序列关系。

## 第 4 页：核心挑战：固定证据假设不适合云负载

基于前面的观察，这一页总结了本文面临的核心挑战。

云工作负载的困难不只是“曲线复杂”，更关键的是同一个服务在不同时间窗口中会切换运行状态，导致模型可以依赖的预测证据也在变化。如果模型默认总是相信同一种信息源，比如一直相信历史周期，或者一直相信邻居关系，那么在状态切换处就容易出现系统性误差。

这里主要有四个挑战。

第一个挑战是状态非平稳。同一个 workload 的局部均值、方差和波动幅度会随时间改变。在一个窗口中看起来异常的高负载，在另一个窗口中可能已经成为新的正常水平。也就是说，模型不能简单把数值大小当作固定意义来理解。

第二个挑战是突发稀疏但代价高。尖峰通常只持续少数时间点，在训练样本中占比不高，但是它会显著放大 MSE，并且对扩缩容和 SLA 风险影响很大。如果预测模型把尖峰平滑掉，实际系统就可能扩容不及时。

第三个挑战是跨序列关系会临时出现。多个实例之间可能在某些时段同步变化，但这种关系不是固定拓扑。今天两个实例一起波动，不代表它们在所有时间都相关。因此，图关系需要动态构建，而不是预先固定。

第四个挑战是历史模式会失效。当当前窗口偏离过去学习到的典型形态时，继续按照旧周期或旧原型外推，会把漂移误认为周期，把状态变化误认为噪声。

所以，MPG-Former 的核心目标是：在不同窗口状态下，动态判断哪类证据更可靠，并据此完成预测。

## 第 5 页：研究方案——任务描述

接下来介绍模型方法。

首先是任务定义。MPG-Former 的输入是一个历史工作负载窗口，记作 `X`。在当前实验设置中，一个窗口长度是 72，其中前 48 个时间点是历史输入，后 24 个时间点是未来预测位置。

如果用张量维度表示，可以写成：

`X ∈ R^{B×72×C}`。

这里 `B` 表示 batch size，也就是一次训练或推理中同时处理多少个窗口；`72` 表示每个窗口包含 72 个时间点；`C` 表示动态特征数量，例如 target workload、CPU 相关特征、资源状态特征等。

模型真正要预测的是未来 24 个时间点的目标 workload，也就是：

`ŷ ∈ R^{B×24}`。

需要注意的是，训练时数据里确实有未来 24 个真实值，但它们只作为监督标签使用。模型输入中未来 target 会被 mask 掉，不能直接泄露给模型。真实部署时，模型只需要看到过去 48 个历史点，以及可用的上下文特征，然后输出未来 24 步预测。

因此，这个任务可以理解为：给定当前窗口的历史状态，预测接下来 24 个时间点的目标负载。

## 第 6 页：Target RevIN + History Representation Generation

这一页是模型的输入预处理和历史表示生成过程。

首先，模型从 encoder input 中提取 target channel，也就是目标 workload 通道。假设输入是 `x_enc ∈ R^{B×48×C}`，其中 48 是历史长度，C 是动态特征数量。模型取出第 0 个通道作为目标历史：

`x_w = x_enc[:, :, 0]`，

因此 `x_w ∈ R^{B×48}`。

然后模型对 target window 做窗口级归一化。具体来说，对每个样本窗口单独计算均值和标准差：

`μ_w = mean(x_w)`，  
`σ_w = std(x_w)`。

然后得到归一化后的目标通道：

`x̃_w = (x_w - μ_w) / (σ_w + ε)`。

这样做的目的，是减少不同窗口之间尺度变化的影响。比如某个窗口整体处于高负载，另一个窗口整体处于低负载，如果直接建模原始数值，模型很容易把尺度差异和形态差异混在一起。Target RevIN 只对目标通道做归一化，其他动态特征保持不变。

接着，模型把归一化后的 target channel 放回原来的 encoder input，得到 normalized encoder input。

之后进入 History Representation Generation。原始输入每个时间点只有 C 维特征，模型先通过 Linear Projection 把它映射到 `d_m` 维，通常是 128 维。然后加入 positional encoding，让模型知道每个 token 在 48 个历史时间点中的位置。

如果有静态上下文，比如机器类型、应用类型或实例信息，模型还会通过 Gated Static Context 把这些静态信息融合进每个时间点的表示中。最后经过 LayerNorm，得到历史高维表示：

`H_s ∈ R^{B×48×d_m}`。

这里的 `H_s` 是后续时间证据分支真正处理的高维历史序列。

## 第 7 页：Temporal Evidence Branch

这一页是时间证据分支，主要回答一个问题：模型如何从当前 workload 自身历史中提取预测证据。

这个分支的输入有两个。第一个是 `H_s ∈ R^{B×48×d_m}`，它是前面生成的高维历史表示；第二个是 `target_history ∈ R^{B×48}`，也就是目标通道过去 48 个点的真实历史值。

首先，模型根据 target_history 计算窗口统计量，包括均值 `μ_w` 和标准差 `σ_w`。这些统计量会输入一个 MLP，生成两个自适应参数 `τ_w` 和 `δ_w`，用于调制 attention。

接着，模型对 `H_s` 做 Q、K、V 投影：

`Q, K, V = Proj(H_s)`。

然后计算非平稳 attention：

`A = softmax(τ_w · QK^T / sqrt(d_h) + δ_w)`，  
`AttnOut = A · V`。

这里的意思是，不同窗口的波动程度不同，attention 的集中程度和偏置也应该不同。比如波动大的窗口可能需要更关注局部关键点，而稳定窗口可以更平滑地利用历史信息。

然后模型做 Moving Average 分解：

`Trend = MA(H_s)`，  
`Seasonal = H_s - Trend`。

Trend 表示低频趋势，也就是比较平滑的长期变化；Seasonal 表示高频残差，包括周期扰动、短期波动和局部异常。

之后进入 Short-term Temporal Encoder。这里用两个卷积核大小不同的 Conv1D：`k=3` 捕捉非常短的局部变化，`k=5` 捕捉稍宽一点的短期波动；BiGRU 负责建模相邻时间点之间的顺序变化。最后把这些信息 concat 起来，再通过 Linear 映射回 128 维。

时间分支最后得到两个结果：一个是 encoded history，仍然保留 48 个时间点的高维表示；另一个是 `c_time`，它是对 48 个时间点做汇总后的时间证据向量，维度是 `B×d_m`。

直观来说，`c_time` 表示“当前窗口自己的历史中，哪些时间依赖和短期变化最有用”。

## 第 8 页：Multi-scale Prototype Branch

这一页是多尺度原型分支，主要回答第二个问题：当前窗口是否像某种典型负载模式。

这个分支的输入是 `target_history ∈ R^{B×48}`。模型会把 48 个历史点按照四种尺度切分：

`p ∈ {6, 12, 24, 48}`。

当 `p=6` 时，48 个点会被切成 8 个 patch，每个 patch 长度是 6；当 `p=12` 时，会切成 4 个 patch；当 `p=24` 时，会切成 2 个 patch；当 `p=48` 时，整个窗口就是 1 个 patch。

每个尺度都会同时提取时域和频域信息。以 `p=6` 为例，模型不是让 8 个 patch 分别匹配 prototype，而是先对每个 patch 做 Linear 映射，再对 8 个 patch token 求平均，得到这一尺度的时域 token。同时，模型会对每个 patch 做 rFFT，得到频域幅值，再经过 Linear 并求平均，得到频域 token。

然后时域 token 和频域 token 相加，形成该尺度的 scale token，记作 `Z_s`。

接下来，`Z_s` 会去匹配可学习的 Prototype Memory。每个尺度都有一组 prototype，模型通过点积相似度和 softmax 得到当前窗口与这些 prototype 的匹配权重。匹配到的原型再和当前 scale token 融合，通过 Recover 模块得到该尺度的原型表示。

四个尺度各自得到原型表示后，模型通过 scale weights 判断哪个尺度更重要，再聚合得到：

`c_proto ∈ R^{B×d_m}`。

除此之外，模型还会通过 `Linear(c_proto)` 生成：

`future_padding ∈ R^{B×24}`。

这个 future_padding 不是最终预测结果，而是给 decoder 的未来 24 个 target 位置提供一个初始轮廓。最终结果还需要经过后面的 Transformer Decoder 修正。

所以，原型分支的作用可以概括为：从历史窗口中检索典型负载形态，并为未来预测提供形态先验。

## 第 9 页：Dynamic Graph Branch

这一页是动态图分支，主要回答第三个问题：batch 内其他相似 workload 是否能为当前窗口提供外部证据。

在这个分支中，一个 batch 里的每个窗口都被看作一个图节点。如果 batch size 是 64，那么当前图中就有 64 个节点。图不是固定的，而是在每个 batch 中动态构建。

动态图分为两条路。

上路由根据 `target_history` 构建 workload graph。具体来说，模型计算不同窗口之间 target_history 的相似度，例如 cosine similarity，然后保留 top-k 个最相似的邻居，得到 `workload_adj`。

下路由根据 static context 构建 context graph。如果有机器、应用或实例信息，就用这些静态上下文计算相似度；如果没有静态上下文，也可以使用窗口统计特征来构建。得到的邻接矩阵是 `context_adj`。

有了两张图之后，模型分别对 `c_time` 做 GCN 或 message passing。

上路由得到：

`z1 = GCN_w(c_time, workload_adj)`。

下路由得到：

`z2 = GCN_c(c_time, context_adj)`。

这里的 `z1` 和 `z2` 已经不是图本身，而是经过图消息传递后的节点表示。它们表示当前窗口在不同图视角下吸收了相似窗口信息后的结果。

最后，模型把 `z1` 和 `z2` 通过 Concat、Linear、GELU 和 LayerNorm 融合成：

`c_graph ∈ R^{B×d_m}`。

直观来说，如果当前窗口和 batch 中其他几个窗口最近走势很像，那么图分支会把这些相似窗口的信息聚合过来，作为跨序列证据。

## 第 10 页：Drift-aware Fusion and Forecasting

这一页是最终融合和预测部分。

到这里，模型已经得到了三类证据：

`c_time` 表示时间证据，来自当前 workload 自己的历史；  
`c_graph` 表示图证据，来自 batch 内相似窗口；  
`c_proto` 表示原型证据，来自可学习的典型负载形态。

接下来，Drift-aware Router 根据这三类证据，以及由 target_history 计算出的漂移特征，生成三个权重：

`w_time`、`w_graph`、`w_proto`。

这三个权重经过 softmax 后相加为 1。融合公式是：

`c_fused = w_time · c_time + w_graph · c_graph + w_proto · c_proto`。

也就是说，模型不是固定平均三类证据，而是根据当前窗口状态决定更相信谁。比如稳定周期窗口可能更依赖时间证据和原型证据；协同波动窗口可能更依赖图证据；如果原型匹配不确定，模型就会降低对 prototype 的依赖。

然后，`c_fused` 会增强 encoded history。代码里对应的逻辑可以理解为：

`Enhanced Memory = encoded + proj(c_fused)`。

这样 decoder 在做 cross-attention 时，看到的不只是原始历史编码，还包含了三类证据融合后的上下文。

另一方面，`c_proto` 会通过 Linear 生成 future_padding，填入 decoder input 的未来 24 个 target 位置。decoder input 由 last 12 history 和 future_padding 组成。

最后，Transformer Decoder 根据 enhanced memory 和 decoder input 生成未来表示，再通过 Prediction Head 输出：

`Point forecast ∈ R^{B×24}`。

这个 point forecast 就是模型最终预测的未来 24 个时间点目标 workload 值。

## 第 11 页：感谢观看

最后总结一下。

MPG-Former 的核心思想是：云工作负载预测不是固定证据源的时间外推，而是一个漂移感知的动态证据选择问题。

为了解决这个问题，模型设计了三类证据分支。时间分支从自身历史中提取趋势、局部变化和短期依赖；原型分支通过多尺度时频 patch 匹配典型负载形态；图分支从 batch 内相似窗口中获取跨序列证据。最后，漂移感知 router 根据当前窗口状态动态决定三类证据的融合权重，并由 decoder 输出未来 24 步预测。

我的汇报到这里结束，谢谢各位老师和同学，欢迎大家批评指正。

## 补充答辩话术

### 1. 如果被问：为什么不是直接用 Transformer？

可以回答：

普通 Transformer 主要强调时间依赖建模，但云 workload 的难点不仅是时间依赖，而是不同窗口中可靠证据会变化。比如稳定周期窗口可以靠历史节律，突发窗口要关注短期局部变化，协同波动窗口需要看相似实例，漂移窗口则需要判断历史模式是否还可靠。因此 MPG-Former 在 Transformer 基础上显式加入了原型证据、图证据和漂移感知路由。

### 2. 如果被问：future_padding 是不是最终预测？

可以回答：

不是。future_padding 是原型分支根据 `c_proto` 生成的未来 24 步初始轮廓，它用于填入 decoder input 中被 mask 的未来 target 位置。最终预测还要经过 Transformer Decoder 和 Prediction Head，所以 future_padding 更像是 decoder 的先验提示，而不是最终输出。

### 3. 如果被问：prototype memory 是怎么来的？

可以回答：

prototype memory 是模型内部的可学习参数，不是每个 batch 临时生成的。它在训练开始时随机初始化，然后通过反向传播不断更新。每个尺度都有自己的 prototype memory，因此模型可以分别记住短尺度、中尺度和长尺度的典型负载形态。

### 4. 如果被问：Dynamic Graph 中的节点是什么？

可以回答：

节点不是单个时间点，而是一个 batch 里的一个 workload 窗口。比如 batch size 是 64，那么当前动态图有 64 个节点。边是根据窗口之间的相似度动态构建的，top-k 相似窗口会成为邻居。

### 5. 如果被问：漂移特征来自哪里？

可以回答：

漂移特征来自 target_history，而不是 H_s。模型会根据目标通道过去 48 个点计算最后值偏离程度、平均变化幅度、标准差以及 prototype entropy 等信息。这些特征输入 router，用来判断当前窗口是否稳定、突发、漂移或原型匹配不确定。
